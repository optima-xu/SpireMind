# Agent 决策质量复盘与优化建议

日期：2026-10-04。范围：现有多 Agent 架构、最近三段铁甲战士 A0 续局、实机使用的记忆数据库。此次只做离线复盘，没有调用模型、发送游戏动作或新开对局。

后续实现与验收见[鲁棒性改造报告](ROBUSTNESS.md)。本文保留改造前的观察与建议；修复范围、实际学习状态和新性能数字以该报告为准。

当前最值得投入的是战斗效果覆盖、可信数值和经验学习闭环。本地准备已经很快，但模型仍会误解实时数值；本局的组合搜索又被未支持的能力整体跳过，实机记忆库没有形成学习规则。继续增加提示文字或打开 thinking，不能单独解决这些问题。

## P0：让数值具有来源，并补上决策后的语义校验

本局重复出现“实时数值已经包含加成，模型又加一次”的错误。现有提示已经要求避免重复计算，但原始表达式计算器只保证算式算对，无法证明输入数值来自正确对象。

| revision | 模型理由 | 相邻公开状态中的实际结果 |
| --- | --- | --- |
| 200 | 挑衅提供 `10 + 3 = 13` 格挡 | 格挡从 0 到 10 |
| 202 | 防御提供 11，累计 21，完全防住 21 来伤 | 格挡从 10 到 18，只增加 8 |
| 203 | 打击造成 30 | 碾碎爪 HP 从 101 到 82，只减少 19 |
| 209 | 双重打击造成 69 | 碾碎爪 HP 从 82 到 38，只减少 44 |
| 217 | 全身撞击造成 37 | 碾碎爪 HP 从 38 到 10，只减少 28 |

建议增加统一的 `ActionEvaluation`：绑定当前 revision、牌实例、目标、效果来源和可信度，区分牌面实时数值、目标数值、推算值及未知值。计算器增加读取当前状态的动作比较能力；模型传入动作引用或比较目标，受支持的战斗数值由本地核算层提供。

Coordinator 在合法性校验后增加语义校验：阻止可证明的自杀动作、错误的斩杀承诺和已证明可避免的致死结束回合。未知效果继续保持未知。模型理由用于审计，不能作为安全证明，也不应仅靠自然语言正则决定执行。

主要位置：`core/decision.py`、`strategies/tactics/effects.py`、`strategies/tactics/assessment.py`、`runtime/validator.py`、`providers/openai.py`。

验收：固定上述五个状态，核对格挡和伤害来源；测试敌我加成归属、目标专属数值、取整、1 HP 卖血，以及未知效果不能被伪装成精确结论。当前轮已用现有代码离线重放 revisions 177 / 200 / 209 / 215 / 225，确认未知能力会阻止组合规划，1 HP 的突破仍被评估为 `self_lethal`。

## P0：补齐实际牌组与 Boss 的组合机制

这段运行出现的 `plating_power`、`pyre_power`、`unmovable_power`、`surrounded_power` 尚未进入已支持集合。任一未支持玩家能力会使整个生存组合搜索跳过；攻击规划还要求只有一个存活敌人。普通战斗和双敌 Boss 因此都很容易退回模型逐张选择。

revision 209 是清晰的牌序问题：手中有 0 费狂怒、双重打击和两张各提供 8 格挡的防御，已有狂怒每次攻击提供 5 格挡。模型先攻击，随后防御，最后才打狂怒。本回合实际累计 21 格挡，16 HP 面对 36 来伤，下一回合剩 1 HP。

按当前公开手牌作局部重排：先打第二张狂怒，再攻击，两张防御不变，攻击触发格挡增加 5；合计 26 格挡、结算后 6 HP。这是局部牌序推算，没有实际重跑，也不证明最终可以获胜。

建议按本局频率扩展效果模型：

- 覆甲的回合末格挡、薪火之源的回合开始回能、坚定不移的首次格挡翻倍。
- 狂怒叠加与攻击触发、全身撞击随当前格挡变化、武装改变后续牌的数值。
- 遭到包围与朝向变化、双敌目标选择、同伴死亡触发蟹之怒后的格挡和力量。
- 抽牌和消耗选择形成规划边界：执行到抽牌后重新观察，不猜测隐藏抽牌顺序。

不要把这些 ID 直接加进白名单。每个能力需要实现效果、触发阶段、资源消耗和组合回归。未支持能力应标记它影响的计算范围，让独立可证明的事实继续可用；无法证明的完整路线仍输出 `unknown`。

Combat 改为生成少量当前回合候选序列，再选择攻防折中。已证明的短序列每一步重新绑定当前合法动作；抽牌、未知触发、资源变化或预测与实际不符时立即重规划。`WorkingMemory.current_plan` 当前只有声明、排除和清空，没有完整的生产和执行路径，不应认为已有跨动作规划能力。

主要位置：`strategies/tactics/{effects,search,assessment}.py`、`strategies/combat.py`、`memory/working.py`。验收覆盖狂怒牌序、格挡转伤害、双敌击杀后的新威胁和搜索上限；不以强行减少 `unknown` 的数量作为通过标准。

## P1：让分层记忆学到战术，先接通历史经验

实机 `runs/memory.sqlite` 的检查结果：498 条已核验 Episode，全部属于同一个 seed 分组；36 个复盘作业为 complete，但 `lessons`、`lesson_history` 和历史导入记录均为 0。当前 `reflection_use_model=false`。

这里并非没有读取记忆：181 个上下文中，110 个包含两条经验示例，71 个不含示例；全部不含学习规则。`L4_experience` 被标记裁剪或部分省略 90 次。演示数据库的学习结果不能证明实机数据库已经接入历史。

更深一层的问题是学习内容。目前 `LessonProposal` 只支持 HP、Block、deck count 和 gold 的局部差值；模型复盘也只能提出这些指标，最终文字又会被改写为“某条件下发生某差值”。它适合记录效果观察，但无法表达“先狂怒后攻击”“换牌药水应在能利用新手牌时使用”或“保护当前回合必要格挡牌”的战术经验。只打开模型复盘仍受这个限制。

建议保留现有分层和安全门控，增加两类不同用途的经验：

1. **效果观察**：继续按版本、角色、状态条件核验，记录数值和证据，供事实核算使用。
2. **战术经验**：保存公开场景条件、候选顺序、实际结果、局部可核验替代方案、反例和置信度；提供条件化建议。执行层只采用通过当前状态重新核算的动作。

完整战斗结束后，Reflection 汇总整个战斗的关键决策，优先复盘伤害预期不符、药水无收益、明显牌序损失及低 HP 选择。不要只取最近几条动作，也不要把“最终死亡”当作所有上游决策错误的证明。

跨 Agent 归因继续使用现有 handoff：Combat 报告防御无法及时出现、费用拥堵和资源消耗；Run 对选牌/移除/升级提出候选解释；Map 对路线风险提出候选解释。整局战略结论在独立 seed 和留出集上验证之后再提高权重。

检索先过滤敌人、阶段、当前危险、可用手牌和相关能力，再排序。当前 FTS 检索包含整个牌组的公开符号，基础牌可能使相似度与本回合战术无关。保留版本过滤、证据引用和反例停用；条件泛化需要明确效果依赖，不能简单删除所有能力条件。

首先将已有历史导入实际使用的学习库，并检查启动时的 seed 分组、导入来源、active/candidate 数量和最终 prompt 是否真的携带经验。同 seed 续跑仍只算一组；不要降低三个独立 seed 的激活门槛来制造“学到了”的表象。

此次在新建的隔离影子数据库中运行已有导入和聚合逻辑：读取 34 段 live trace、13 个 seed 分组，固定 9 组训练 / 4 组留出；导入 2,892 条记录，其中训练集 888 条、留出集 1,062 条已核验。聚合生成 2 条 active 效果观察，未修改实机数据库。这个结果证明历史接入路径能够工作，也说明目前的学习内容仍很窄。合并未来数据时需确保同一个 seed 始终属于同一个分区。

主要位置：`memory/{experience,reflection,manager}.py`、`context/compiler.py`、`cli.py`。验收应分别记录复盘完成、提案产生、验证通过、检索命中、进入上下文和影响决策的数量。

## P1：减少重复请求，为关键经验留出上下文

最新一段记录 181 个模型上下文和 474 次 HTTP 请求；每个决策经常需要计算器往返和最终选择。本地准备 P50 只有约 31 ms，进一步微调缓存难以改变以秒计的决策等待。

`L1_current_state` 平均约 11,237 个 UTF-8 字节，`L5_task` 平均约 4,038 字节。`progress_view()` 当前会把完整 trigger progress 投影进上下文，其中重复的 schema、来源、note 和展示说明不都是决策所需信息。保留实时计数、阈值、未知机制描述及全部合法动作，按当前触发阶段投影相关字段；将支持范围和候选路线作为结构化内容，减少任务文字里的重复 JSON 和无效候选细节。

优先让本地核算给出少量有证据的候选路线与未知点，再交给 Combat 选择。仍需模型计算时，把相关比较合并成一次工具调用，继续支持当前 required 计算器设置。已证明的短计划可逐步重新核验执行，遇到抽牌或未知事件后再请求模型。经验注入要记录实际保留的项目，避免“检索到了”却在上下文裁剪时丢失。

主要位置：`context/{views,compiler}.py`、`providers/openai.py`、`strategies/combat.py`。验收分别比较有效决策的 HTTP 次数、实际 usage、端到端耗时和固定场景选择，不用少发请求替代质量验证。

## P1：修复恢复计时，并使停顿可解释

`20261003T024939-cb0ba042` 最后一次结束回合遇到 `TransitionPending`；下一状态已经进入第 11 回合，之后无动作的步骤耗时 179.04 秒，最终以 `environment_failure_seconds=180.05` 退出。最后一个模型请求被取消，Provider 故障计时为 0。

源代码在环境恢复窗口内用 `asyncio.timeout(remaining)` 包住整个 `step()`，其中也包含成功观察后的模型请求。这会把合法但较慢的推理算成持续环境故障。此次用一秒窗口的离线假环境复现：观察成功、模型等待被取消、结果为 `error_limit`，Provider 故障为 0。

建议将观察、推理、派发和对账分成明确阶段。环境重试窗口只计环境 I/O 的故障与恢复；观察成功就结束对应故障段。模型故障使用自己的计时，pending 继续对账，不能重发不确定动作。保留用户要求的 180 秒恢复窗口和当前关闭的运行总步数、总时间、总 token 上限。

进度增加执行阶段、当前请求耗时、最近心跳及进程身份，并区分 paused / waiting_model / retrying / stopped。缺失总结且 writer 已不存活时标记异常中止，不能继续显示旧 `running`。

Provider 还应区分已回传 usage、未知用量的保守预算占用和明确 HTTP 拒绝。当前 `_completion()` 对所有没有增加 usage 的异常都累计完整估算额度，403 记录也可能被算入 token 总量；预算保守估算不应被展示成已确认计费。

主要位置：`runtime/{agent,control,progress}.py`、`providers/openai.py`、`providers/protocols.py`。

## P2：让构筑与资源策略按边际收益评价

本局第 33 层拥有 28 张牌，仍有 5 张基础打击。第 31 层选取双重打击+的理由是“严格升级现有双重打击”，但奖励操作增加新副本，并不替换旧牌。额外攻击可能有价值，不能仅凭这个理由认定选牌错误；应显式比较增加后的费用、抽到关键防御的概率和跳过的收益。

另一明确的资源问题发生在 revision 177：0 能量时使用赌徒特酿，理由说为下一回合换牌；revision 178 又确认空选择，实际上没有换牌。药水被消耗却没有产生所声称的收益。

建议 Run 提供结构化 Boss 计划：关键引擎、启动成本、必要防御/抽牌密度、需要保留的资源和有效期限。Combat 返回实际启动回合、费用拥堵、防御缺口和药水利用率，供 Run 更新判断。Map 使用相同的构筑与资源反馈。抽牌概率只根据公开的无序牌堆组成估计，不读取隐藏顺序。

主要位置：`strategies/run.py`、`context/route_horizon.py`、`memory/manager.py`。先做离线候选比较与药水语义回归，再用不同 seed 验证长期效果。

## 推荐实施顺序与质量验收

1. 修正恢复计时、用量分类和进度阶段；接通历史经验并核对实际数据库与上下文。
2. 加入有来源的动作效果、语义校验，以及本局高频能力和双敌规划。
3. 用关键战斗片段实现战术复盘、检索和短计划执行；在未知处重新观察。
4. 再改构筑/路线评价，并做独立 seed 的消融比较。

保留 Coordinator + Combat / Run / Map / Event + Reflection 的角色分工。Combat 内部增加规划、评价与校验职责；只有困难局面才考虑额外模型审查，避免每个动作再增加一轮模型请求。

先验收公开状态回归：数值来源、牌序损失、药水实际收益、选牌语义、未知能力和取消恢复。再比较无经验、仅 Episode、加入战术经验的离线表现，记录支持范围、改选动作和反例。若进行模型对照，继续遵守原定最多 24 次决策、80 次 HTTP 请求、40 万 token 的评测预算，保持模型、thinking 和工具设置一致。

实机统计应以不同 seed 的完整局为单位，分别报告胜负、到达楼层、每场失血、未支持机制、错误退出、每次有效决策的请求和 token。当前同 seed 续局只能定位问题，不能证明 thinking 开关、经验模块或这些建议提高了胜率。
